2. Enterprise Solution Architecture

Enterprise Solution Architecture covers the complete business and technology ecosystem.

Business Requirements ↓ NFRs ↓ Domain / Bounded Context ↓ Application Architecture ↓ Integration ↓ Data ↓ Security ↓ Cloud / Infrastructure ↓ Observability ↓ DR / Cost

Enterprise Architecture vs Microservices

Enterprise Solution Architecture Microservices Architecture
Complete enterprise solution Application/service architecture
Business, data, security, integration, cloud and operations Service boundaries, communication and deployment
Broad architectural scope Focused application architecture
Can include monolith, microservices, serverless and SaaS One architectural style
Interview statement: Enterprise Solution Architecture defines the overall ecosystem, while Microservices Architecture defines how an application can be decomposed into independently deployable business services.

4. Microservices Architecture

Why Microservices?

"Instead of building one large monolithic application, I would decompose the system based on business capabilities into smaller, independently deployable services.

This enables independent development, deployment, scaling and fault isolation.

However, I would not choose microservices by default. I would first evaluate business boundaries, scalability, deployment independence and operational complexity."

How Do You Define Microservice Boundaries?

Business Capability → Bounded Context → Service Boundary → Data Ownership

Example: 


E-Commerce
    |
    +-- Customer Service
    |
    +-- Product Service
    |
    +-- Order Service
    |
    +-- Payment Service
    |
    +-- Inventory Service

Boundaries should be based on business responsibilities, not technical layers such as Controller Service Repository.

When Should You NOT Use Microservices?

If the system is small, has limited scalability requirements, requires simple transactions and is managed by a small team, a modular monolith may be a better choice.

7. AKS & Kubernetes

Why AKS Instead of App Service?

AKS is appropriate when we need Kubernetes orchestration, container-level control, workload isolation, complex deployment strategies or advanced scaling.

If those capabilities are unnecessary, App Service can be simpler and reduce operational overhead.

Payment Provider Idempotency

17. 60-Minute Mock Interview — Complete Sequence

Practice these questions in this order. Answer each in approximately 30–60 seconds.

Question 1 — Tell me about yourself.

"Tell me about yourself and your architecture experience."

Focus on .NET, Azure, Microservices, API, Messaging, Security, Data and Architecture leadership.

Question 2 — Walk me through your architecture.

Start: Business → NFR → Front Door → APIM → Entra ID → AKS → Microservices → Service Bus → SQL/Redis → Observability → DR.

Question 3 — Why Microservices?

Independent deployment, scaling, fault isolation and team autonomy — but only when the business requirements justify the complexity.

Question 4 — How do you define service boundaries?

Business capability + bounded context + data ownership.

Question 5 — Why database per service?

Independent data ownership and reduced schema coupling.

Question 6 — Why APIM?

Centralized API security, throttling, rate limiting, versioning, policies and governance.

Question 7 — Front Door vs APIM?

Front Door = global edge and routing. APIM = API management and policy enforcement.

Question 8 — How does JWT validation work?

Entra ID issues the token. APIM validates signature, issuer, audience, expiry and required claims/scopes.

Question 9 — REST vs Service Bus?

REST for immediate response. Service Bus for asynchronous, decoupled workflows.

Question 10 — Queue vs Topic?

Queue = competing consumers. Topic = publish/subscribe.

Question 11 — Explain Outbox Pattern.

Store business data and event in the same transaction, then asynchronously publish the event.

Question 12 — Duplicate messages?

Idempotent consumer using EventId/IdempotencyKey and durable processing state.

Question 13 — Payment provider double charge?

Use a stable provider-supported idempotency key, payment state persistence, webhooks and reconciliation.

Question 14 — Payment succeeds but Order update fails?

Saga with retries and compensating action such as refund or payment reversal.

Question 15 — Orchestration vs Choreography?

Orchestration is preferred for complex multi-step workflows requiring centralized state, retry and compensation.

Question 16 — Why AKS?

Kubernetes orchestration, containers, workload isolation, advanced scaling and deployment capabilities.

Question 17 — Traffic increases 10x?

Identify bottleneck → APIM throttling → HPA → cluster autoscaling → Redis → Service Bus → database/downstream dependency analysis.

Question 18 — One service is down?

Timeout + bounded retry + circuit breaker + fallback or asynchronous processing where appropriate.

Question 19 — How do you avoid cascading failures?

Timeout, retry, circuit breaker, bulkhead, rate limiting, asynchronous communication and graceful degradation.

Question 20 — Slow SQL query?

Execution plan, indexes, statistics, blocking, deadlocks, query design and database capacity.

Question 21 — N+1 query?

Detect repeated database calls and use appropriate projection, joins, eager loading or batching.

Question 22 — Why Redis?

Frequently accessed data where caching improves latency and reduces database pressure.

Question 23 — How do you trace a request across microservices?

Correlation/trace IDs and distributed tracing through Application Insights/OpenTelemetry-compatible instrumentation.

Question 24 — How do you design DR?

Start with RPO/RTO, then design backup, replication, regional recovery and regular DR testing.

Question 25 — Why should we hire you as an architect?

"I don't approach architecture as simply selecting technologies. I start with business requirements and NFRs, evaluate alternatives and trade-offs, and then design for scalability, security, resilience, observability and cost.

I can connect business requirements to implementation across .NET, Azure, microservices, APIs, messaging, Kubernetes and data architecture, while also considering operational and failure scenarios."

Golden Interview Formula

Requirement → Decision → Why → Trade-off → Failure Handling

Example:

"I would use Service Bus because the workflow does not require an immediate response and we need loose coupling. The trade-off is eventual consistency. To handle failures, I use bounded retry, dead-letter handling and idempotent consumers."

Architect Mindset

  • Do not start with technology.
  • Start with business capability.
  • Identify NFRs.
  • Define bounded contexts.
  • Choose synchronous vs asynchronous communication.
  • Define data ownership.
  • Design security.
  • Design failure handling.
  • Design observability.
  • Define DR based on RPO/RTO.
  • Consider cost and operational complexity.
  • Always explain trade-offs.

Final Rule for the Interview

Don't answer: "We use Azure Service Bus because it is scalable."

Instead answer: "The requirement is asynchronous processing and loose coupling, so I use Service Bus. The trade-off is eventual consistency, which I address with idempotency, retries and appropriate monitoring."
