ASP.NET Core DI: Transient vs Scoped — Real-Time Project Usage

Interview goal: Understand not only the definitions, but where and why Transient and Scoped services are used in a real enterprise ASP.NET Core Web API.

1. First Understand the Problem

```

In ASP.NET Core, Dependency Injection (DI) creates and manages objects for us. The important question is:

"How long should this object live?"

Lifetime Object Creation Typical Usage
Transient New instance every time requested Stateless lightweight services
Scoped One instance per HTTP request DbContext, Unit of Work, request-level business services
Singleton One instance for application lifetime Shared/stateless application-wide services, caches, configuration
```

2. Transient Service

```

A Transient service gets a new object every time it is requested from the DI container. 

builder.Services.AddTransient<IEmailService, EmailService>();

Real-Time Example: Email Formatter

Imagine an Order API. After an order is created, we need to generate an email message. 

public interface IEmailTemplateService
```

{
string CreateOrderConfirmation(int orderId, string customerName);
}

public class EmailTemplateService : IEmailTemplateService
{
public string CreateOrderConfirmation(
int orderId,
string customerName)
{
return $"Order {orderId} confirmed for {customerName}";
}
}
```

Register it as:

builder.Services.AddTransient
<IEmailTemplateService, EmailTemplateService>();

Why Transient?

  • The service is stateless.
  • It does not own database state.
  • It does not need to survive the request.
  • Each operation can safely receive a fresh instance.
  • It is lightweight.
```

3. Scoped Service

```

A Scoped service is created once per HTTP request. Every component requesting that service during the same request gets the same instance. 

builder.Services.AddScoped<IOrderService, OrderService>();

Real-Time Example: Order Service

public interface IOrderService
```

{
Task CreateOrderAsync(Order order);
}

public class OrderService : IOrderService
{
private readonly AppDbContext _db;

```
public OrderService(AppDbContext db)
{
    _db = db;
}

public async Task CreateOrderAsync(Order order)
{
    _db.Orders.Add(order);

    await _db.SaveChangesAsync();
}
```

}
```

Register:

builder.Services.AddScoped<IOrderService, OrderService>();
```

builder.Services.AddDbContext(options =>
{
options.UseSqlServer(connectionString);
});
```

DbContext is normally Scoped because it represents a request-level unit of work and tracks entities during that request.

```

```

Suppose one customer sends: 

POST /api/orders

ASP.NET Core creates a DI scope for that HTTP request.

  1. Create OrderController.
  2. Resolve IOrderService.
  3. Create one OrderService for this request.
  4. Resolve AppDbContext.
  5. Use the same DbContext during the request.
  6. Resolve the transient email service when needed.
  7. Complete the request.
  8. Dispose scoped objects.
```

5. Important Difference — Same Request

```

Consider this:

public class OrderService
```

{
private readonly IEmailTemplateService _email1;
private readonly IEmailTemplateService _email2;

```
public OrderService(
    IEmailTemplateService email1,
    IEmailTemplateService email2)
{
    _email1 = email1;
    _email2 = email2;
}
```

}
```

If registered as Transient:

AddTransient<IEmailTemplateService, EmailTemplateService>

Then:

_email1 != _email2

They are normally two different instances.

If the same service is registered as Scoped: 

AddScoped<IEmailTemplateService, EmailTemplateService>

Then within the same request:

_email1 == _email2

The same instance is reused within that request scope.

```

9. The Most Important Rule

```

Dependency Lifetime Rule

A service should generally not depend on a service with a shorter lifetime in a way that causes the shorter-lived service to be captured incorrectly.

The classic problem is: 

Singleton
|
+-- Scoped Service  ❌

A Singleton lives for the entire application lifetime, while a Scoped service belongs to an individual request. Capturing the Scoped service directly inside the Singleton creates a lifetime mismatch.

This is why you should understand the lifetime hierarchy before choosing a DI lifetime.

```

10. Interview Scenario

```

Question

"You have OrderService, Repository and DbContext. Which lifetime will you choose?"

Strong Interview Answer

"I would normally register the DbContext as Scoped because EF Core's DbContext represents a request-level unit of work. The Repository and OrderService that depend on that DbContext would also normally be Scoped. For stateless lightweight services such as validators, calculators or DTO transformation services, I would prefer Transient. The decision is based on state ownership, request boundaries and resource lifetime rather than simply choosing a lifetime by convention."

```

11. Easy Memory Trick

```
Think About Lifetime
"Give me a fresh object every time." Transient
"Give me one object for this HTTP request." Scoped
"Give me one shared object for the application." Singleton
```

12. 30-Second Interview Answer

```

Transient creates a new instance every time the service is requested, so I use it mainly for lightweight, stateless services such as validators, calculators and formatters.

Scoped creates one instance per HTTP request, so I use it for request-level services such as DbContext, repositories, Unit of Work and business services that participate in the same operation.

In a real Order Management API, OrderService, Repository and DbContext would typically be Scoped, while PriceCalculator and EmailTemplateService could be Transient.

```

Key Takeaway

Transient = fresh instance.
Scoped = one instance per HTTP request.
Choose based on state, ownership and resource lifetime.
