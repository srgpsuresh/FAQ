ASP.NET Core DI: Transient vs Scoped

Interview Goal: Understand not only the definitions, but where and why Transient and Scoped services are used in a real enterprise ASP.NET Core Web API.

1. Understand the Problem

Dependency Injection creates and manages objects for us. The important question is:

How long should this object live?
Lifetime Object Creation Typical Usage
Transient New instance every time requested Stateless lightweight services
Scoped One instance per HTTP request DbContext, Unit of Work, request-level services
Singleton One instance for application lifetime Shared application-wide services

2. Transient Service

A Transient service gets a new object every time it is requested from the DI container. 

builder.Services.AddTransient<
    IEmailTemplateService,
    EmailTemplateService>();

Real-Time Example: Email Template Service

public interface IEmailTemplateService
{
    string CreateOrderConfirmation(
        int orderId,
        string customerName);
}

public class EmailTemplateService
    : IEmailTemplateService
{
    public string CreateOrderConfirmation(
        int orderId,
        string customerName)
    {
        return $"Order {orderId} confirmed for {customerName}";
    }
}

Why Transient?

  • Stateless service
  • No database state
  • Lightweight
  • No request-level state required
  • Fresh instance is acceptable

3. Scoped Service

A Scoped service is created once per HTTP request. Every component requesting that service during the same request receives the same instance. 

builder.Services.AddScoped<
    IOrderService,
    OrderService>();

Real-Time Example: Order Service

public interface IOrderService
{
    Task CreateOrderAsync(Order order);
}

public class OrderService : IOrderService
{
    private readonly AppDbContext _db;

    public OrderService(AppDbContext db)
    {
        _db = db;
    }

    public async Task CreateOrderAsync(Order order)
    {
        _db.Orders.Add(order);

        await _db.SaveChangesAsync();
    }
}

Registration

builder.Services.AddScoped<
    IOrderService,
    OrderService>();

builder.Services.AddDbContext<AppDbContext>(
    options =>
    {
        options.UseSqlServer(connectionString);
    });
Interview Point: DbContext is normally registered as Scoped because it represents a request-level unit of work and tracks entities during that request.

Suppose a customer sends: 

POST /api/orders
  1. ASP.NET Core creates the HTTP request scope.
  2. OrderController is created.
  3. IOrderService is resolved.
  4. OrderService gets a scoped DbContext.
  5. Repository uses the same DbContext.
  6. EmailTemplateService gets a transient instance.
  7. Order is saved.
  8. The request finishes.
  9. Scoped objects are disposed.

5. Same Request — Important Difference

public class OrderService
{
    private readonly IEmailTemplateService _email1;
    private readonly IEmailTemplateService _email2;

    public OrderService(
        IEmailTemplateService email1,
        IEmailTemplateService email2)
    {
        _email1 = email1;
        _email2 = email2;
    }
}

Transient

AddTransient<
    IEmailTemplateService,
    EmailTemplateService>();

Normally: 

_email1 != _email2

Two different instances are created.

Scoped

AddScoped<
    IEmailTemplateService,
    EmailTemplateService>();

Within the same HTTP request: 

_email1 == _email2

The same scoped instance is reused.

  • Validators
  • DTO mappers
  • Formatters
  • Price calculators
  • Email template builders
  • Stateless helper services
  • Data transformation services

  • Entity Framework Core DbContext

9. Important Lifetime Rule

⚠️ Avoid Lifetime Mismatch

Be careful when a longer-lived service captures a shorter-lived service. 

Singleton
    |
    +-- Scoped Service  ❌

A Singleton lives for the entire application lifetime, while a Scoped service belongs to an individual request.

Therefore, directly injecting a Scoped service into a Singleton is generally invalid and can cause incorrect lifetime behavior.

10. Interview Question

Q: OrderService, Repository and DbContext — which lifetime will you choose?

I would normally register the DbContext as Scoped because EF Core's DbContext represents a request-level unit of work.

The Repository and OrderService that depend on that DbContext would also normally be Scoped.

For lightweight stateless services such as validators, calculators and DTO transformation services, I would use Transient.

The decision should be based on state ownership, request boundaries and resource lifetime.

11. Easy Memory Trick

Think Lifetime
"Give me a fresh object every time." Transient
"Give me one object for this HTTP request." Scoped
"Give me one shared object for the application." Singleton

12. 30-Second Interview Answer

Transient creates a new instance every time the service is requested, so I use it mainly for lightweight, stateless services such as validators, calculators and formatters.

Scoped creates one instance per HTTP request, so I use it for request-level services such as DbContext, repositories, Unit of Work and business services participating in the same operation.

In a real Order Management API, OrderService, Repository and DbContext would typically be Scoped, while PriceCalculator and EmailTemplateService could be Transient.

🎯 Key Takeaway

Transient = Fresh instance

Scoped = One instance per HTTP request

Choose the lifetime based on state, ownership, request boundaries and resource lifetime.
