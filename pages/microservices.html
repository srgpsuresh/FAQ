Top Interview FAQs

Use the following questions to prepare for .NET Microservices Architect and Senior Developer interviews.

1. Why do we need Design Patterns in Microservices?
Interview Answer
  • Reduce code duplication.
  • Solve recurring software problems.
  • Improve maintainability.
  • Increase scalability.
  • Promote loose coupling.
  • Improve testability.

Real-Time Example: Order Service communicates with Shipping Service using Publish-Subscribe instead of direct API calls.

2. Which design patterns are commonly used in Enterprise Microservices?

3. Why is CQRS used?
Problem:

Read and Write operations often have different performance and scalability requirements.

Solution:
  • CreateOrderCommand
  • UpdateOrderCommand
  • GetOrderQuery
  • GetOrderHistoryQuery

Benefit: Independent scaling and optimized read/write models.

4. Why do we use MediatR / Mediator Pattern?

Without Mediator

    |
Repository

With Mediator

Controller
    |
Mediator
    |

    |
Repository

Purpose: Reduce coupling and keep controllers thin.

5. Why Repository Pattern instead of EF Core directly?

The Repository Pattern prevents application/domain logic from being tightly coupled to a specific persistence implementation.

  • Loose coupling
  • Easy unit testing
  • Database abstraction
  • Cleaner business logic
6. What problem does Saga Pattern solve?

Order Processing Scenario

Create Order
Reserve Inventory
Process Payment
Create Shipment

If payment fails, the inventory reservation may need to be released.

Answer: Saga manages a distributed business transaction through local transactions and compensating actions.

7. Why Outbox Pattern?
Problem:

The database transaction succeeds but publishing the Kafka event fails.

Solution:
  1. Save Order.
  2. Save Event into Outbox table.
  3. Commit database transaction.
  4. Background Worker publishes event.

This provides reliable event delivery, although consumers should still be designed for idempotency.

8. Why Event-Driven Architecture? 
Order Service
      |
     Kafka
   /   |    \
  /    |     \
Inventory Payment Shipping

Services communicate through events instead of being tightly coupled through synchronous calls for every business action.

  • Loose coupling
  • Independent scalability
  • Asynchronous processing
  • Better resilience
9. Why Strategy Pattern?

Strategy Pattern allows the application to select an algorithm at runtime.

10. Why Factory Pattern?

Factory hides object creation logic from the calling application. 

ShippingFactory.Create("FedEx");

ShippingFactory.Create("DHL");

ShippingFactory.Create("UPS");
11. Why State Pattern?

State Pattern is useful when an entity's behavior changes based on its current state. 

Pending
   ↓
Paid
   ↓
Packed
   ↓
Shipped
   ↓
Delivered

Each state can control which operations are allowed.

12. Why Specification Pattern?

Specification encapsulates reusable business rules and allows them to be combined.

  • Customer Active?
  • Credit Available?
  • Stock Available?
  • Address Valid?
13. Why Adapter Pattern?

Different courier providers may expose different APIs and request formats.

Courier Adapter
FedEx FedExAdapter
DHL DHLAdapter
BlueDart BlueDartAdapter

The application works with one common interface while adapters translate provider-specific requests.

14. Why Circuit Breaker?
Problem:

Shipping API is continuously unavailable.

Circuit Breaker prevents repeated calls to an unhealthy dependency.

  • Stops repeated calls.
  • Allows the dependency time to recover.
  • Can return fallback behavior.
  • Protects system resources.
15. Why Retry Pattern?

Retry handles transient failures such as temporary network errors or short-lived service unavailability.

  • Retry up to 3 times.
  • Use exponential backoff.
  • Add jitter where appropriate.
  • Stop retrying after the configured limit.
16. Why Cache-Aside Pattern? 
Check Redis
    |
    +---- Found ------> Return
    |
    +---- Not Found
             |
         Database
             |
        Update Redis
             |
          Return

Cache-Aside reduces database load and improves response time for frequently requested data.

17. Why Dependency Injection?

A class should depend on abstractions rather than creating its own concrete dependencies. 

Instead of:

new OrderRepository();

Prefer:

IOrderRepository repository;

This improves loose coupling, testing and maintainability.

🎯 Interview Tip

Do not explain design patterns only with definitions. Pick one enterprise scenario such as Order → Payment → Inventory → Shipping and explain where each pattern is applied, what problem it solves, and what trade-off it introduces.

A strong Architect-level answer follows:

Problem → Pattern → Implementation → Benefit → Trade-off
