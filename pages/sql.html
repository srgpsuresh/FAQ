1. Important SQL Differences – FAQ

DELETE vs TRUNCATE vs DROP

Question One-Line Interview Answer
DELETE vs TRUNCATE DELETE removes selected rows; TRUNCATE removes all rows faster and resets identity.
DELETE vs DROP DELETE removes data; DROP removes the entire table including its structure.
TRUNCATE vs DROP TRUNCATE keeps the table structure; DROP removes the table completely.
WHERE vs HAVING WHERE filters rows before grouping; HAVING filters groups after aggregation.
GROUP BY vs DISTINCT GROUP BY groups rows for aggregation; DISTINCT removes duplicate results.
INNER JOIN vs LEFT JOIN INNER JOIN returns matching rows; LEFT JOIN returns all left rows plus matching right rows.
UNION vs UNION ALL UNION removes duplicates; UNION ALL keeps duplicates and is generally faster.
EXISTS vs IN EXISTS checks whether a matching row exists; IN compares against a set of values.
ROW_NUMBER vs RANK ROW_NUMBER gives unique numbers; RANK gives the same rank to ties and skips numbers.
RANK vs DENSE_RANK RANK skips numbers after ties; DENSE_RANK does not skip numbers.
CTE vs Temp Table CTE is a query expression for a statement; a temp table stores reusable intermediate data.
Clustered vs Nonclustered Index Clustered index determines the table's row storage order; nonclustered index is a separate structure pointing to rows.
CHAR vs VARCHAR CHAR has fixed length; VARCHAR has variable length.
ISNULL vs COALESCE ISNULL accepts two expressions; COALESCE can evaluate multiple expressions and returns the first non-NULL value.

2. SQL Performance & Optimization Techniques

Top Performance Best Practices

  1. Avoid SELECT *

    Select only the required columns to reduce I/O and network traffic.

  2. Use Proper Indexes

    Create appropriate indexes on frequently filtered, joined and sorted columns.

  3. Make Queries SARGable

    Avoid applying functions to indexed columns inside WHERE conditions.

  4. Filter Early

    Use WHERE conditions to reduce the number of rows processed as early as possible.

  5. Use UNION ALL When Appropriate

    Use UNION ALL when duplicate removal is not required because UNION performs duplicate elimination.

  6. Use Appropriate JOINs

    Join only the required tables and ensure appropriate indexes exist on join columns.

  7. Avoid Unnecessary DISTINCT

    DISTINCT can introduce additional sorting or hashing; use it only when duplicate removal is required.

  8. Return Only Required Rows

    Use appropriate filtering and pagination instead of returning large datasets.

  9. Keep Transactions Short

    Short transactions reduce locking, blocking and deadlock risks.

  10. Update Statistics

    Accurate statistics help the optimizer choose better execution plans.

  11. Check Missing Index Suggestions Carefully

    Validate index recommendations against workload and existing indexes before creating them.

  12. Avoid Over-Indexing

    Too many indexes increase storage requirements and slow INSERT, UPDATE and DELETE operations.

3. SARGability – Important Interview Topic

What is SARGable?

A SARGable predicate allows SQL Server to efficiently use an index to locate required rows.

Bad Example


```

SELECT *
FROM Employee
WHERE YEAR(JoiningDate) = 2026;
```

Better Example


```

SELECT *
FROM Employee
WHERE JoiningDate >= '20260101'
AND JoiningDate <  '20270101';
```

Interview Point: Avoid wrapping indexed columns inside functions when possible.

4. SQL Server Execution Plan

What is an Execution Plan?

An execution plan shows how SQL Server's optimizer intends to retrieve and process data for a query.

Simple Flow

  1. SQL query is submitted.
  2. SQL Server parses and validates the query.
  3. Query Optimizer evaluates possible execution strategies.
  4. Optimizer chooses an execution plan based on estimated cost.
  5. SQL Server executes the selected plan.
  6. Actual execution statistics can be compared with estimates.

Important Execution Plan Operators

Operator Interview Meaning
Index Seek Efficiently finds qualifying rows through an index.
Index Scan Reads many or all index rows; may be appropriate depending on selectivity.
Table Scan Reads the table without using an index.
Key Lookup Uses a nonclustered index and then looks up additional columns in the base table.
Nested Loops Often effective when one input is small and the other input has a useful index.
Hash Match Commonly used for larger joins or aggregations when suitable indexes are unavailable.
Sort Sorts rows for ORDER BY, grouping, ranking or other operations.
Filter Removes rows that do not satisfy a predicate.

5. How to Analyze an Execution Plan

  1. Check Actual vs Estimated Rows

    Large differences can indicate stale statistics, parameter sensitivity or incorrect cardinality estimates.

  2. Look for Table Scans

    Determine whether a scan is expected or whether a suitable index could reduce unnecessary reads.

  3. Look for Expensive Operators

    Investigate operators with high cost, CPU, I/O or row counts.

  4. Check Key Lookups

    Many repeated lookups may indicate that a covering index could be useful.

  5. Check Sort Operations

    Large sorts can consume CPU and memory and may sometimes be reduced through appropriate indexing or query design.

  6. Check Warnings

    Review spills, implicit conversions and other execution-plan warnings.

  7. Check Logical Reads

    Use SET STATISTICS IO to understand how much data SQL Server reads.

  8. Check CPU and Duration

    Use SET STATISTICS TIME and monitoring tools to identify CPU-intensive or long-running queries.

6. Real-Time SQL Optimization Flow

  1. Identify the slow query.
  2. Capture the actual execution plan.
  3. Check logical reads, CPU time and duration.
  4. Compare estimated rows with actual rows.
  5. Check scans, seeks, lookups, joins and sorts.
  6. Check indexes and statistics.
  7. Check for non-SARGable predicates.
  8. Rewrite the query if necessary.
  9. Add or modify indexes only after analysis.
  10. Test again and compare before/after performance.

7. Top Interview One-Line Answers

Q: How do you optimize a slow SQL query?
I check the actual execution plan, logical reads, CPU, statistics, indexes, joins and SARGability, then test query/index improvements and compare the results.
Q: Index Seek vs Index Scan?
Index Seek retrieves qualifying rows efficiently; Index Scan reads many or all index rows.
Q: What is a covering index?
A covering index contains all columns required by a query, potentially avoiding additional lookups.
Q: Why can SELECT * hurt performance?
It can read and return unnecessary columns, increasing I/O, memory usage and network traffic.
Q: What is SARGability?
SARGability means writing predicates so SQL Server can efficiently use indexes to locate qualifying rows.
Q: Why are statistics important?
Statistics help the optimizer estimate row counts and choose an efficient execution plan.
Q: Why avoid too many indexes?
Extra indexes consume storage and increase the cost of INSERT, UPDATE and DELETE operations.
Q: Actual vs Estimated Execution Plan?
Estimated shows what the optimizer expected; Actual shows what happened during execution and includes runtime information.

  • Scan → Read many/all rows
  • Lookup → Fetch missing columns
  • Statistics → Help optimizer estimate rows
  • Index → Faster data access
  • SARGable → Index-friendly predicate
  • Short Transaction → Less blocking
  • Actual Plan → See what really happened
