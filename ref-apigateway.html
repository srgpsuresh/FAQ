API Gateway

20 practical points covering purpose → request flow → security → traffic management → resilience → observability → interview scenarios.

```
Client API Gateway Security / Policies Microservice Response
```
One-line interview definition: API Gateway is the single entry point between clients and backend services. It centralizes cross-cutting concerns such as routing, authentication, authorization, rate limiting, transformation, resilience and observability.
```

1What is API Gateway?

An API Gateway sits between external clients and backend APIs/services. Instead of exposing every microservice directly, clients call the gateway.

Why? One controlled entry point instead of exposing multiple internal services.

Interview: "Gateway hides internal service topology from clients."

2Why do we need it?

Without a gateway, a mobile/web client may need to know the URLs of Customer, Order, Payment and Product services individually.

Gateway gives the client one endpoint and centralizes common policies.

3Single Entry Point

Example: https://api.company.com

Internally the gateway can route requests to: /orders, /customers, /payments.

Clients do not need to understand the internal microservice network.

4Request Routing

The gateway examines the incoming path, method, host or other routing information and forwards the request to the appropriate backend. 

GET /api/orders/100
    ↓
```

API Gateway
↓
Order Service
```

Purpose: Centralize service discovery and routing rules.

5Authentication

The gateway can validate credentials such as JWT/OAuth tokens or API keys before forwarding a request.

Invalid requests can be rejected at the edge instead of consuming backend resources.

Typical answer: "Authenticate as early as possible."

6Authorization

Authentication answers "Who are you?". Authorization answers "What are you allowed to do?". 

JWT
```

↓
Validate user
↓
Read role/scope
↓
Allow / Reject request
```

Fine-grained authorization can be applied according to route, method, caller or scope.

7Rate Limiting

Rate limiting controls how many requests a client can make in a period. 

Client
```

↓
100 requests/sec allowed
↓
Gateway
↓
Extra requests → 429 Too Many Requests
```

Protects backend services from accidental overload, abusive clients and traffic spikes.

8Throttling & Quotas

Rate limit controls request rate. Quota controls allowed usage over a larger period.

Example: 100 requests/sec plus 1 million requests/month.

Scenario: Premium customers can receive higher limits than standard customers.

9Load Balancing

If multiple instances of a service exist, the gateway can distribute traffic among available instances. 

Gateway
```

├── Order-1
├── Order-2
└── Order-3
```

Improves scalability and availability.

10Request Transformation

The gateway can modify headers, paths, query parameters or payload formats before sending a request downstream.

Example: /v1/customer → internal /customer-service/api/customer

Useful when external and internal API contracts are different.

11Response Transformation

The gateway can transform backend responses before returning them to the client.

Example: hide internal fields, normalize headers or adapt response formats.

Prevents internal implementation details from leaking outside.

12Caching

Frequently requested, relatively stable data can sometimes be cached at the gateway or edge. 

Client
```

↓
Gateway
↓
Cache HIT → Response

Cache MISS
↓
Backend
↓
Cache + Response
```

Reduces backend calls and improves response time.

13Circuit Breaker

If a backend repeatedly fails, the gateway/resilience layer can stop sending requests temporarily. 

Order Service failing
    ↓
```

Circuit OPEN
↓
Do not continuously call service
↓
Return controlled failure / fallback
```

Prevents repeated calls from creating cascading failures.

14Timeout & Retry

The gateway can enforce reasonable upstream timeouts and, where safe, retry transient failures.

Important: Do not blindly retry every operation. Retrying a non-idempotent payment request can create duplicate business effects.

Good answer: "Retry only transient failures and only where the operation is safe or idempotency is guaranteed."

15Observability

Gateway is an excellent point to capture common telemetry:

  • Request/response metrics
  • Latency
  • Status codes
  • Correlation/trace IDs
  • Access logs
  • Error rates

It provides a centralized view of API traffic.

16Security at the Edge

Gateway can be combined with TLS, WAF, IP restrictions, mTLS and other security controls. 

Internet
```

↓
WAF / DDoS protection
↓
API Gateway
↓
Authentication
↓
Microservices
```

Reject malicious or invalid traffic before it reaches business services.

17API Versioning

The gateway can expose multiple API versions while routing them to different backend implementations. 

/api/v1/orders → Order Service V1
```

/api/v2/orders → Order Service V2
```

Allows gradual migration without immediately breaking existing clients.

18BFF / Aggregation

A Backend-for-Frontend can tailor APIs for different clients such as Web, Mobile or Partner applications. 

Mobile
```

↓
Mobile BFF
├── Customer
├── Orders
└── Payments
↓
Combined response
```

Reduces chatty client-to-service communication and allows client-specific API contracts.

19API Gateway Failure Scenario

Because the gateway becomes a central entry point, its availability is critical.

Production design should avoid a single gateway instance. Use a highly available deployment, health checks, scaling and appropriate regional/ multi-zone architecture.

Interviewer: "What happens if the API Gateway goes down?"
Answer: "It can become a single point of failure, so I deploy it redundantly with health monitoring and automatic failover."

Interview Memory Chain

```

Remember API Gateway using this sequence:

ENTRY → SECURITY → CONTROL → ROUTING → RESILIENCE → OBSERVABILITY

  1. ENTRY: Single entry point
  2. SECURITY: Authentication + Authorization + WAF/TLS
  3. CONTROL: Rate limiting + Throttling + Quotas
  4. ROUTING: Route + Load Balance + Transform + Version
  5. RESILIENCE: Timeout + Retry + Circuit Breaker + Cache
  6. OBSERVABILITY: Logs + Metrics + Traces + Correlation ID

30-second interview answer:
"In our microservices architecture, API Gateway is the single entry point for clients. It handles routing to the appropriate service and centralizes cross-cutting concerns such as JWT authentication, authorization, rate limiting, throttling, request transformation and observability. For resilience we apply timeout, controlled retry and circuit-breaker patterns. It also supports versioning, caching and, where appropriate, BFF/aggregation. This keeps the microservices focused on business logic while the gateway manages common API concerns."
